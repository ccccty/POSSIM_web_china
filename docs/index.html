02 / PIPELINE

一次推演，真实发生了什么

没有贴图、没有预烘焙动画：37 帧中的每一帧，都是同一套公式在 1188×864 个格点上重算一遍。

  1. 01

    路径插值

    12–17 个 3/6 小时报点，按 np.interp 分段线性插到逐小时；移速与移向由相邻点中心差分得出，位置与移向不会自相矛盾。

  2. 02

    Holland 风场

    梯度风 V(r) 由中心气压差与最大风速半径决定；四象限 r34/r50/r64 各自展开，台风不对称性被保留。

  3. 03

    增水三件套

    静压平衡的反气压项 + 风应力增水（拖曳系数随风速分段）+ 波增水（有效波高换算），逐格点叠加。

  4. 04

    天文潮叠加

    M2 / S2 / K1 / O1 四个分潮按 η = Σ A·cos(ωt + φ) 合成，与风暴增水线性叠加成总水位。

  5. 05

    淹没判定

    总水位高于地面高程即淹没，深度 = 水位 − 高程；再做 4 连通斑块过滤，丢掉不含海岸种子的孤立噪点。

  6. 06

    分级渲染

    按 0–0.33 / 0.5 / 1 / 2 / 3 / 5 m 七级配色渲染成 RGBA 叠加图，交给 Leaflet 贴合经纬度铺在底图上。

03 / RESPONSE

参数一改，结果真的会动

把山竹整条路径的 Vmax 从 75 kt 一路拧到 165 kt，其余参数不动，重算 7 次。下面两条线是每次的峰值增水与峰值淹没面积 —— 这不是换图，是真的在算。

峰值增水 m 峰值淹没面积 ha

读这条线的三个要点

1 · 单调但不线性。增水随 Vmax 近似线性爬升（1.33 → 2.36 m），面积却在 150 kt 之后突然加速（21,193 → 34,484 ha）。因为面积受地形阈值控制，水位再抬 10 cm 就可能多淹几千公顷。

2 · 面积不能当精度证据。珠江口围田高程多在 0–1 m，总水位差 10 cm 就能让面积跳变，所以比较两套内核时必须比增水，而不是比面积。

3 · 这张表是离线算出来的。线上站点直接读这 7 组结果；本地跑 python server.py 可以自己拖滑块重算任意参数。

04 / TWO KERNELS

把原厂 DLL 直接接进浏览器后端

POSSIM 3.0 的物理内核是编译好的 storm_surge_physics.dll（x64 + gfortran 静态链接）。 它不需要 GUI、不需要 .NET —— 按 C# 里的 P/Invoke 签名用 ctypes 调起来就直接跑，一帧 0.69 s，8 线程 37 帧 7 秒。 于是同一份 DEM、同一帧参数，可以拿两套内核互相对拍。

峰值淹没面积20,846 ha14,758 ha

实现numpy 向量化ctypes 直连 DLL

差 1.4 倍，但不是常数偏差

把台风压在网格中心（pc 900 / 110 kt）：内核 1.057 m，numpy 只有 0.745 m —— numpy 反而偏低 30%。
台风在 119 km 外（山竹真实最近距离）：内核 0.276 m，numpy 0.438 m —— numpy 反而偏高 59%。

原因在径向衰减的形状：原厂风增水是 0.0291572 × W 的一次项，与水深、风区无关；numpy 版按风应力平方走二次项。近中心二次项偏小、远处偏大，交叉点自然落在中间。

顺带把原厂子公式反解出来了：风增水 0.0291572·W、波增水 7.6e-4·W²（W>15 起算）、拖曳系数分段线性。scripts/probe_kernel_physics.py 可复现。

06 / DATA & LIMITS

哪些是真的，哪些是示意

这个项目最容易被追问的地方，恰好也是最该写清楚的地方。

数据项来源性质
地形 DEMAWS Terrain Tiles（NASA SRTM 1″）重采样至 94.3 m真实
底图ArcGIS World Imagery（WGS84）/ 高德矢量兜底真实
台风路径手工编排，量级参考 JTWC / JMA / CMA 最佳路径历史重放，非预报
增水本地按 Holland 公式计算，非外部数据公式有出处，量级经标定
天文潮4 个分潮常量表示意值
村庄15 个真实地名 + DEM 吸附坐标，人口户数为示意半真

这是情景演示，不是水动力模型。没有接 ECMWF/GFS 预报场，没有潮波方程数值求解，潮位在全区用同一个标量。它适合演示「一场台风会把多少平方公里推上水面」「两套内核算出来的差在哪」，不适合用于防汛调度与决策。
